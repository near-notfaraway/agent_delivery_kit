# 集成验收

用固定的当前交付修订贯通真实生产者和消费者，判断确认需求与方案中的整体验收是否成立。输出可复核证据及返工范围，不以本地通过替代目标环境验收。

可由 mainAgent 或通用/专业验收 subAgent 执行，输入输出、固定版本及资源/writer 边界遵循 [委派约定](../delivery-flow/references/agent-delegation.md)。受委派时修复、例外和整体状态请求交回 mainAgent。

## 1. 恢复验收范围与交付修订

读取适用规则、确认需求/方案、有效决策、任务证据和当前交付记录。协调者在全部任务 `completed` 或有依据的 `skipped` 后进入最终 `verifying`；已具备前置的局部集成可提前执行，不能因此宣布整体通过。

按 [当前修订与恢复约定](../delivery-flow/references/recovery-and-corrections.md)，优先读取 `delivery.json.repositories[].delivery_commit`；缺失时回退相关任务 `result.commit`。原任务提交与修复后的当前交付提交分别保留，不由分支最新 HEAD 推断已交付内容。

验证每个 commit 真实存在、对应 Review/批准和验证齐备，所需依赖/产物可按固定版本获取并被下游解析。列明 R / C / V、实际组件、环境与必需外部验收条件。跳过任务仍需证明下游不需要其产物。

## 2. 准备隔离且可运行的链路

先按 [验证与证据约定](../delivery-flow/references/validation-and-evidence.md) 核查工具链、初始化、测试副作用、网络/数据库目标和资源归属。使用已交付 commit 的固定源码或产物，不修改活跃工作树、控制状态或真实业务数据。

读取 [产物管理](../delivery-flow/references/artifact-management.md)，使用分配的 attempt、当前证据入口和 runtime。临时源码副本、数据库数据目录、测试二进制、浏览器预览和缓存使用 runtime，必要结果保存到历史证据目录；创建前记录归属及停止/清理条件，不每轮长期保留完整运行环境。

记录实际框架/编码器、操作系统与架构、时区、相关依赖、配置摘要和启动命令。隔离数据库、集合、账号、端口等按实际需求准备，不机械增加基础设施。

明确真实组件与 Mock 边界、本地和目标环境差异。需要替代服务时说明哪些合同仍经过真实代码，哪些成立条件未验证。没有对应证据不能将模拟权限、存储或部署行为当作目标环境结果。

按 Case 选择可执行的工具或人工操作并记录证据要求，外部 Skill 可选。没有首选工具时可换用能验证相同合同的实现；缺少必要真实资源或证据时保留该项待验，继续独立 Case，不以工具替换自动批准环境例外。

## 3. 贯通真实契约与验收场景

选择方案中的关键场景，经实际入口、默认中间件/编码器和真实消费者验证，而非只在各层 Mock 间比较 DTO。至少覆盖本次相关的正常响应、无结果/空值和错误信封，检查传输与业务错误是否被正确消费。

按相关性扩展：

- 可信身份、权限和环境边界：区分入站认证与下游身份，验证关键 helper 的默认和降级路径。
- 持久化、时间与并发：使用隔离真实存储验证原子条件更新、失败不写数据、冲突和有效时间；Mock 不能证明数据库原子性。
- 依赖消费：在下游实际模块解析/构建中验证固定版本或产物，不以生产者本地 commit 存在证明可消费。
- 浏览器：使用可用自动化工具（如 Playwright、agent-browser）或由人工在实际浏览器按相同 Case 执行。配套浏览器 Skill 可选，使用时遵守实际指令。核对请求、响应、页面与持久化，记录修订、环境、操作者、时间、步骤、预期/实际结果及必要截图和请求/数据证据；工具 click/fill 或口述“已通过”不能替代这些结果。没有浏览器能力或必要证据则保持该项待验，不能改用 Mock 自动通过。

测试数据须经过真实传输。HTTP 请求头可能被规范化，浏览器元素可能在视口外；以实际发送和展示结果修正测试操作。仅当实现违反合同才修业务代码，不能为了错误的夹具或断言改动正确逻辑。

为每个场景记录前置、操作、预期、实际、源修订、结果和关键证据。失败保留其原始结果，定位生产者、消费者、存储或操作问题；先完成独立可验场景，再向协调者交接修复。

## 4. 返工与受影响范围复验

交回协调者的修复需含原因、原任务/仓库、影响合同、下游范围和失败证据。按 [恢复与返工约定](../delivery-flow/references/recovery-and-corrections.md) 默认复用原需求 worktree，保留原任务 `result`，不发明 `reopen` 或直接修改任务图。

修复经 [delivery-review](../delivery-review/SKILL.md) 复核、覆盖范围的实际授权和真实提交后，由协调者记录 correction 并更新当前交付修订。集成必须重新读取当前指针及有效决策，使用修复后的版本复验受影响场景。

按冻结证据判断重验范围：代码、依赖或配置有变化则重验相关场景；纯提交或路径变化且内容、依赖和运行条件等价时，核验并关联已有证据。不能凭“改动很小”复用失败或不等价的结果。

## 5. 形成验收结果与清理

使用 [integration_template.md](assets/integration_template.md)，默认 `validation/integration.md`，保留一个当前入口并按产物管理链接关键失败、修复和最终通过。复用多个 attempt 的结果时说明覆盖及源码/配置等价依据，不把部分复验写成全部 Case 重新执行。沿用已有验收入口，避免每轮生成竞争的最终报告。

报告当前固定修订、需求覆盖、真实链路、Mock 边界、通过与未验证范围、例外/延期的真实批准、兼容与必要回退。缺少必需真实环境或外部首页验证时，明确“代码阶段已交付，整体验收待完成”等事实，不能自动缩减验收。

成功、失败或取消后均按产物管理保存必要证据、核验自有服务退出和临时资源处理。分别记录进程停止、目录删除、必要产物保留及清理失败/未执行，核查链接与摘要未因处理断开；在当前验收入口说明遗留、归属和后续条件，不能仅停止服务就写“数据库已清理”。正式工作树、支撑镜像、历史记录、业务数据和外部资源的删除不属于临时清理权限。

将实际结果交给协调者。全部必需条件满足后由协调者生成交付报告并更新整体阶段；本 Skill 不执行部署、外部发送或自行批准例外。

> 用当前交付的固定修订执行跨仓库验收，经过真实 handler、默认编码器和消费者，记录隔离存储及必要浏览器证据；缺陷交回原需求工作区修复后复验。
