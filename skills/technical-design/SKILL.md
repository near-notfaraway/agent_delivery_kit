# 技术方案设计与评审

以已确认需求及仓库事实为基线，采用 [自带标准模板](assets/design_template.md)，在一个技术设计阶段内完成一份 `design.md`。第 1–7 节面向销售、运营、产品、不同职级及各技术模块接口人，供共同评审实现方向；第 8 节面向能够阅读前文的开发者，定义完整字段、接口和具体实现。两部分共用版本和方案基线，不增加独立设计阶段。

## 调用范围与阶段边界

先按 [delivery-flow 的入口判定](../delivery-flow/SKILL.md#2-定位交付入口并判定新建或恢复) 核验本次需求基线及真实确认依据。当前需求目录及有效交付记录不存在，且只有用户提供的参考文档时，先使用 `requirement-analysis` 新建需求稿；不得把旧需求/预调研方案及其批准当作本次确认。需求尚未确认时整理或补全可审阅稿，必要事实核查可以继续，但不越过需求确认阶段开展技术设计。会话已有明确覆盖当前版本的需求确认时直接沿用，不重复请求。

需求入口统一为 `requirement.md`，采用 [requirement-analysis 自带模板](../requirement-analysis/assets/requirement_template.md)。从本次需求第 7 节读取当前确认版本与范围，从第 6 节识别属于技术设计的待核查事项；已核实的同一交付沿用原文档，不为恢复额外生成副本。来源文件中的确认页不替代当前需求确认。需求事项已澄清不等于整稿已确认。

本 Skill 的职责终点是技术评审稿及其真实评审状态。确认后的执行由协调者按有效授权继续，不因技术方案确认自动获得开发、分支或控制目录写入权。

由 mainAgent 直接执行或委派给通用/专业 subAgent，输入输出、路径和 writer 遵循 [委派约定](../delivery-flow/references/agent-delegation.md)。受委派时将业务选择与整稿确认请求返回 mainAgent；下文的用户对话由 mainAgent 组织，实际反馈按分配的文档范围写回。用户直接使用本 Skill 时可直接澄清，不自动获得整体协调权。

## 1. 恢复材料、版本和边界

读取工作区指令、本次需求正文、已核实的当前方案与评审结论，以及按 [来源材料管理](../delivery-flow/references/source-materials.md) 登记的参考输入。分别提取本次文档版本/确认和来源版本/用途，明确保存位置、仓库职责、分支约定及当前阶段；参考方案是设计输入，不自动成为当前 design.md。

沿用已有名称、版本约定和授权位置，不自行换名、创建分支或要求用户重复提供能查到的资料。文档基线变化时记录影响，不把旧方案的确认扩展到新版本。

参考资料优先使用已收录的固定版本，也可通过平台读取工具、可选文档 Skill 或用户提供的完整本地导出获取。影响契约或决定的新增来源按来源材料管理登记，必要原文交由协调者收录；受委派时仅写分配的来源范围。无需特定外部 Skill；缺少决策所需的资料时标明待核实，不由搜索摘要推断正文。

只处理当前需求相关内容，不为了凑章节扩大功能、仓库或基础设施范围。真实业务材料保存在授权需求位置；公共 Skill、模板和示例只保留通用规则，不复制内部资料、链接、私有路径、代码、账号或凭证。

遵循 [产物管理](../delivery-flow/references/artifact-management.md)，优先更新 design.md 和引用已有来源；详细设计集中在该文件第 8 节，外部对接材料仅按实际需要生成并说明用途，不每轮另建评审副本或调研报告。纯文档阶段不为布局创建 attempt/runtime，确认快照由协调者按执行门禁管理。

## 2. 围绕需求核查现有实现

对相关仓库做有边界的只读调研。优先定向搜索，并行读取独立材料，避免无界扫描、重复调研或反复猜测不存在的路径。

先检查仓库指令、当前分支、修订和未提交改动，记录分析基线。没有 Git 或材料不完整时如实说明；本地分支不代表生产版本或后续开发基线。

按相关性追踪入口、调用链、数据结构、业务层、SDK、持久化、鉴权和前端交互。区分需要修改、仅作依据以及其他团队负责的组件。

重点核查：

- 已有能力能否复用，包括通用转发、请求封装、错误响应、版本更新及资源初始化。
- 字段和身份如何跨组件传递，可信身份来自何处，权限及环境边界在哪里。
- 真实入站路径与下游身份方向分别核实；复用关键 helper 前检查正常和默认/降级分支，不由名称或旧候选架构推断其行为。
- 业务校验、格式校验、环境归属和账号存在性各自的语义，不能相互替代。
- 失败和并发时的真实行为，如条件更新是否检查匹配数量、原子性由何种机制保证。
- 配置保存、下发及实际生效的时机，存量资源和旧客户端如何处理。
- 实际 handler、默认中间件/编码器与消费者如何处理正常、无结果/空值及错误信封；DTO 或 Mock 返回一致不能证明真实传输合同成立。

区分“代码已核实”“用户已明确的系统能力”“待联调验证”，为结论保留代码位置、修订或材料依据。代码中存在配置不代表生产链路已经启用；无法验证的行为保留为待核实。

自行核查实现事实，仅在核查结果影响业务选择或验收口径时直接向用户澄清，并将结论写回同一份 `requirement.md`。沿用已足够的错误处理和查询能力，不将普通实现问题默认扩展为新的用户状态、恢复流程或额外报告。

默认不修改业务代码、不切换分支、不运行会变更依赖或生产数据的命令。优先复用已验证能力；确需增加仓库、协议或基础设施时，先说明原因、证据和最小改动，请用户确认新增范围，同时继续完成独立部分。

## 3. 按标准模板形成一份技术方案

编写前读取本 Skill 的 [assets/design_template.md](assets/design_template.md)，按“背景与目标、当前现状、整体方案、模块职责与协作约定、关键取舍与影响、实施与验证、评审事项、详细设计”组织。参考与证据按需放在附录。既有方案不因模板更新强制迁移，明确授权重组时保留原确认、版本与有效契约。

用户指定历史方案时，实际读取具有代表性的两到三份（可用材料不足时说明）。参考表达方式、图示和评审习惯，在标准模板内组织内容；不复制其他需求的业务结论、架构或功能。用户明确要求调整模板或结构时遵循用户要求。

输出文件名保持 `design.md`，版本记录在文件内；恢复同一交付时沿用原位置与版本，新建方案不沿用参考方案版本或批准。状态如实使用 `待评审 / 修订中 / 待确认 / 已确认`，不能编造作者或确认信息。

标题下仅用一行 Markdown 引用块记录当前需求文档链接及确认版本、更新日期、方案版本和状态，随后直接进入第 1 节。作者、来源索引、阅读说明、生成过程、参考材料关系和历史评审不放在页首。

维护信息按需收在文末附录的 `文档维护信息` 小节中，使用普通 Markdown 标题、简短引用段落和表格组织，不加入 HTML 折叠控件或布局标签。记录实际作者、阅读用途及修订历史，通过链接引用已有来源索引、需求确认和交付记录；确切来源版本、采用范围及生成沿革留在各自已有入口，不重复维护，也不为填写模板另建记录文件。文档整体评审状态在页首显示，第 7 节仅列各事项与状态；实际整稿确认的详细依据放在维护区或引用已有交付记录。影响方案判断的业务规则、协作边界、风险和未决事项仍写在第 1–7 节。

正文直接说明规则、模块职责、条件和结果，不写“以需求 R1、R6 为准”“关联第 4 节 C1”“按 E1 核实”等编号式引导语，也不让模块或评审编号代替名称。必要引用使用能说明内容的链接文字，放在对应结论旁作为依据；读者无需跳转或查编号即可理解当前段落。人工评审稿不附仅用于内部追踪的编号映射表；执行协调需要的对应关系按实际名称或已有编号维护在交付记录或确认后的执行材料中，不为文档组织新增一套代号。用例表可保留稳定编号，但必须同时写明场景名称。

选定的实现方案直接写明采用的机制、处理规则、预期结果和结论，不用“本稿建议”“推荐”等试探措辞表达已经定义的技术行为。方案待评审与事实未核实分别如实记录；证据不足的权限语义、环境能力或生效指标仍保留具体未知条件，不将明确的实现预期写成已验证或已批准。

引用应补充必要技术定义或事实依据。文内小节引用优先直接说明章节或小节标题；不能正常跳转的链接改为文字定位，不为修复跳转插入 HTML 锚点、辅助代码或不可读标记。文件和资料链接按实际可访问性保留，目标不存在、内容不匹配或没有补充信息的引用删除。验证时分别记录文件/目标检查与实际跳转结果，未能操作目标入口时不得将字符串匹配描述为跳转通过。当前段落已经完整说明的行为，不再附加重复跳转或定位说明。

第 1 节明确分为“背景”和“目标”两个小节。背景说明当前场景、问题及影响；目标先说明期望结果，再将本次覆盖的能力和改造范围列为重点，保留必要关键约束。排除范围用简短 Markdown 引用块作范围说明，不与目标重点并列展示；没有需要澄清的排除范围时省略。

第 2 节只说明当前链路、已有能力和缺口。关键事实的依据在对应位置用描述性链接补充，影响判断的未知事实就地注明；不在章末追加“以上为本地代码核查结论”“目标环境仍待实测”等核查或进度总结。分析修订和读取范围留在详细设计或参考依据，验证计划及结果按用途放在实施与验证或详细验证，影响推进的未决条件可以注明，并列在评审事项；引用已有记录，不重复写一段核查汇报。

先形成整体草稿，再展开支撑可行性的关键详细设计，并将细化结果反馈到整体方案。第 1–7 节应可独立阅读，讲清改造前后行为、完整协作链路、关键契约、取舍、依赖和验收重点；不要求参会者靠阅读第 8 节发现重要决策。第 8 节完成必要技术核查，会上无需逐项讲解，开发时作为实现依据；详细设计不能引入前文未披露的新业务规则、协作约定或重要影响。

第 1–7 节避免重复需求、源码分析、完整字段/报文、内部算法、详细用例与执行日志，不用文件清单或技术口号代替机制和结果。第 8 节按主题承接前文，仅补充精确改动、契约、处理与验证，不重述背景、目标、整体架构和选择理由，也不粘贴整份源码或无关 SDK 文档。任务认领、Git 操作和 Agent 编排由独立执行材料承载，SOP 和运行报告按需链接。提交评审前删除填写提示、占位内容和不适用内容，不为填满模板新增工作。

以最小必要改动满足需求。正常、异常、边界与配置生效规则应连贯呈现；需要时使用架构图、流程图或时序图，图文的字段、状态和失败结果必须一致。

## 4. 编写协作约定、详细设计和验收用例

按业务组件组织改动。第 4 节解释各方职责、协作输入输出和关键行为，第 8 节按同一组件定位仓库、文件、入口和类型，说明具体如何调整，不能只列文件名。改动定位基于已核查代码，拟新增位置单独注明。核心逻辑集中，同语义命名一致。正文、图示和协作表使用明确的模块名称，不强制新增组件编号或另列编号对照表。

外部配合未完成时，直接标明“待核实”或“待处理”的具体事项、责任方及必要完成条件，不追加“上述配合尚未全部落实”“不替对方承诺”等自我声明或免责式说明。权限、排期和指标按真实依据记录，未知内容保持具体待办，不编造承诺。

第 5 节聚焦选择理由、收益、代价、具体影响和处理方式。直接影响技术选择的前提在相应取舍中写明，不默认另设“成立条件”汇总；不重复证据状态、验证进度、待办清单或评审流程。删除重复说明前核对是否包含独有约束，必要约束保留在对应取舍、实施依赖或评审事项中。

完整技术契约集中定义在第 8 节，其他章节引用；第 1–7 节仍须说明影响评审判断的关键语义，不能隐藏业务结果、协作边界或风险。字段定义包含类型、实际传输名、单位/范围、来源/可写性、必填/默认与省略/null/空值语义、保存及更新方式；接口包含实际请求/响应信封、校验、错误及调用方消费。涉及并发、跨系统副作用或配置生效时定义精确机制及失败边界。避免多处维护完整字段、响应结构或处理规则，代码和 JSON 示例与唯一契约一致。

首次出现的字段简称、事件代号和协议枚举先说明业务含义，再给出实际传输名称；映射较多时用字段对照表逐项解释。正文以中文说明机制，不堆叠未经解释的代号；保留真实字段及类型，不能为了可读性改写传输契约。

验证用例使用稳定编号（如 V1）及场景名称，覆盖实际涉及的正常、异常、边界、并发、权限、环境隔离、兼容和跨组件验收。第 6 节保留影响方案判断的验证重点，写清场景、前置、操作、预期和责任；第 8 节展开精确输入、错误注入、并发步骤和验证方式，不重复抄写全部需求验收。必要覆盖关系在交付记录或执行材料中维护，删除已有对照时保留可核对的依据。评审稿直接给出验证内容，不追加“以下均为计划”“尚未测试或联调”等阶段声明；实际执行状态和结果在验证记录中如实维护，引用已有结果时注明证据和适用范围。

涉及跨仓库合同，第 6 节说明实际链路及验证责任，第 8 节展开生产者真实入口、默认编码器和实际消费者的验证，包含相关正常、空值和错误响应；数据库原子性使用隔离真实存储，前端交互按需经过实际浏览器。第 8 节写明 Mock 边界、工具链/框架/时区和与目标环境的差异；不能将局部 Mock 或只编译作为真实验收。验证计划与 [integration-validation](../integration-validation/SKILL.md) 衔接，运行和证据按 [共享约定](../delivery-flow/references/validation-and-evidence.md)。

第 6 节说明影响推进的真实依赖、发布顺序、启用条件和回退限制；第 8 节展开下游可消费的固定版本/产物、获取条件、解析验证及兼容/迁移机制，不能仅写本地 commit 或浮动源码路径，也不能编造尚未产生的版本或验证结果。操作按需链接 SOP。不把普通仓库发版凑成外部依赖，不保留不适用的空壳或重复免责声明。

## 5. 准备必要的外部对接材料

仅在其他团队确需独立对接材料时生成，沿用已授权命名与位置，说明职责、调用方式、接口契约、异常处理、联调条件和验收标准。与需求及方案共用同一版本的契约，不额外扩大对方工作范围。

准备材料可以在授权范围内继续完成；发送消息、邮件或提单须有明确授权及可确定的接收目标。

## 6. 处理评审反馈与版本迭代

收到反馈后直接更新已授权的文档，先区分业务规则、技术选择、仓库范围和文档组织方式的变化。

- 用户给出接入方式或范围结论时，将其作为约束继续核查，清理被否决方案的接口、关联改动、测试和发布步骤。
- 用户调整写作方式时，按实际内容重组章节，保留已确认技术契约。
- 详细设计发现新的业务行为、协作契约或重要影响时，同步第 1–7 节及受影响确认；不只在第 8 节追加实现决定。
- 业务语义或验收变化时，写回需求正文并标明受影响确认状态；需要时返回需求澄清。
- 同步需求、方案、外部对接材料及版本引用，不能只追加一段结论而保留旧方案矛盾。
- 更新版本、真实 Review 和文末维护区的变更记录；未核实事项保持待验证，不将文档修改描述为方案通过。

第 7 节的当前评审事项只保留未解决事项，表格使用“模块 / 组件”列，直接填写名称，不填写方案评审人、接口人或核查责任方称谓。已确认结论写回所属章节，并在附录按需保留评审历史；表后不追加重复的“确认记录”或整体状态总结。共同评审聚焦第 1–7 节，第 8 节不要求会上逐项讲解；其必要可行性核查和影响方案的未决条件不得遗漏。

实际整稿确认发生后，在文末维护区记录确认版本、范围、确认人、日期及依据，或引用已有批准记录，由协调者同步 `delivery.json`；尚未确认时不另写待确认段落，整体状态以页首为准。保留原有真实批准，不扩大局部批准，也不把批准当作技术事实已验证，不增加独立详细设计审批门禁。

本 Skill 不创建或修改 `delivery.json`；整体状态由 `delivery-flow` 协调者从初始化开始管理，并同步文档中的真实确认。方案未确认前不生成执行计划或控制目录。已有交付记录及执行快照需要变更时，遵守工作区流程同步确认基线及受影响材料，不直接修改活跃执行状态。

## 7. 输出前润色

每次向用户输出新稿或修订稿前，先在同一份 `design.md` 中完成一轮润色，再执行下一节的交付检查。润色覆盖整体方案和详细设计，沿用已有文档入口、版本和确认约定。环境中有适合技术文体的润色 Skill 时可选用；没有时直接按以下步骤执行。

1. 通读正文，理顺长句、重复、空话和不清楚的指代，使用自然、准确的中文说明机制、条件和结果。保留必要技术术语及正式程度，已经通顺的内容不强行改写。
2. 保留需求范围、技术选择、协作边界、实现预期、风险及依据，不新增事实、实现细节或性能结论，不为缩短篇幅删除独立信息。保留条件、否定、时间和确定程度，区分已核实事实、待验证事项、实现预期与实际批准。
3. 默认保留标题文字与层级、稳定用例编号、表格数据、字段名、类型、代码块、命令、路径、URL、链接目标及原始引文。不得为了可读性改变接口、默认值、空值、错误、并发或配置生效语义；确需调整标题或引用时，按既有文档规范核查受影响引用。
4. 对照润色前的文本逐段核对信息和技术语义，再通读成稿，检查整体方案、详细设计、图示、表格及用例是否一致。发现契约矛盾或证据缺口时，按原核查、评审反馈或变更流程处理，不用措辞掩盖问题。

润色完成不代表方案已验证或获批；实际确认及基线同步仍遵循已有流程。润色后的版本作为交付检查和人工评审的入口。

## 8. 检查与交付

交付前检查：

- 已完成输出前润色，并对照原稿确认信息、技术契约和确定程度未被改变。
- 需求基线、用户已确认结论和最终方案一致，旧假设已清理。
- 当前方案与参考方案明确区分，关键来源的确切版本、读取范围和必要原文可追溯；来源索引或参考批准没有被当成当前阶段确认。
- 字段、接口、状态、时间、错误语义及各文档契约一致。
- 原子性、可信身份、兼容和环境边界有事实依据或明确待核实。
- 组件改动解释充分，用例覆盖关键需求；实际执行结果与验证记录一致，不将计划或文档检查写成业务验收通过。
- 第 1–7 节可独立支撑共同评审，业务变化、协作约定与重要影响未藏在第 8 节；第 8 节能定位具体改动，完整字段、接口、处理与验证足以指导实现，且引用前文而不重复叙述。
- 模板元信息、需求确认版本、方案版本、链接、代码位置及示例正确；页首整体状态、各项评审状态及已有整稿批准依据一致且真实。
- 文档组织符合第 3 节和模板：页首精简、背景与目标分开、维护记录在文末；正文聚焦技术结论，未将独有约束或风险随重复说明一并删除。
- 表达符合第 4 节：模块、规则和用例可直接理解，已定义行为明确，未知条件及外部配合具体；内部追踪关系不挤入评审正文。
- 当前评审事项与第 6 节一致：直接列模块或组件，解决项已写回正文；整稿批准独立可追溯，不由单项状态推断。
- 小节引用用可读标题定位，不依赖 HTML 标签、辅助锚点或行号链接；保留链接可解析且内容匹配，不能可靠跳转时改用文字说明。
- 字段简称、事件代号和协议枚举已解释，真实传输契约未被改写；无填写提示、占位或不适用内容。

执行适当的文档内容与一致性检查，并遵守工作区要求的验证；不为文档整理新增业务测试或宣称通过业务验收。

交付可点击的方案及必要对接材料入口，简述变化、验证结果和未解决事项。只有缺少真实阶段确认时，才请用户评审具体版本。可以交付完整“待评审”稿，不得称为已审批方案；确认后交接技术方案基线，后续执行准备按另行授权和工作区流程处理。恢复旧方案时沿用已有真实确认和版本记录，不因模板更新重建文档或执行状态。
