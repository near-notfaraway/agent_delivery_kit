# 技术方案设计与评审

以已确认需求及仓库事实为基线，采用 [自带标准模板](assets/design_template.md) 编写可独立阅读、可逐节讨论的 `design.md`。面向未参与聊天的产品、开发、测试和运维人员，说明现状、整体方案、模块改动、关键取舍与影响、实施验证及评审事项。

## 调用范围与阶段边界

用户要求将需求转化为技术方案、核查相关实现以形成方案、修改既有方案、按历史方案调整表达方式，或准备外部团队对接材料时使用本 Skill。这里的评审是技术方案评审，不替代代码差异审查。

先检查需求基线及真实确认依据。需求尚未确认时，使用 `requirement-analysis` 整理或补全可审阅的需求稿；必要事实核查可以继续，但不越过需求确认阶段开展技术设计。会话已有需求确认时直接沿用，不重复请求。

需求入口统一为 `requirement.md`，采用 [requirement-analysis 自带模板](../requirement-analysis/assets/requirement_template.md)。从第 7 节读取当前确认版本与范围，从第 6 节识别属于技术设计的待核查事项；旧文档按已有真实记录恢复，不要求为恢复额外生成副本。需求事项已澄清不等于整稿已确认。

本 Skill 的职责终点是技术评审稿及其真实 Review 状态。技术方案确认不自动授权代码开发、创建分支或建立执行控制目录。

由 mainAgent 直接执行或委派给通用/专业 subAgent，输入输出、路径和 writer 遵循 [委派约定](../delivery-flow/references/agent-delegation.md)。受委派时将业务选择与整稿确认请求返回 mainAgent；下文的用户对话由 mainAgent 组织，实际反馈按分配的文档范围写回。用户直接使用本 Skill 时可直接澄清，不自动获得整体协调权。

## 1. 恢复材料、版本和边界

读取工作区指令、需求正文、已有方案和评审结论，提取需求名称、确认版本及依据、文档保存位置、仓库路径与职责、用户指定分支约定、参考方案及当前阶段。

沿用已有名称、版本约定和授权位置，不自行换名、创建分支或要求用户重复提供能查到的资料。文档基线变化时记录影响，不把旧方案的确认扩展到新版本。

参考资料可通过平台读取工具、可选文档 Skill 或用户提供的完整本地导出获取，记录来源、版本与读取范围。无需特定外部 Skill；缺少决策所需的资料时标明待核实，不由搜索摘要推断正文。

只处理当前需求相关内容，不为了凑章节扩大功能、仓库或基础设施范围。真实业务材料保存在授权需求位置；公共 Skill、模板和示例只保留通用规则，不复制内部资料、链接、私有路径、代码、账号或凭证。

遵循 [产物管理](../delivery-flow/references/artifact-management.md)，优先更新 design.md 和引用已有来源；详细子方案及对接材料仅按实际需要生成并说明用途，不每轮另建评审副本或调研报告。纯文档阶段不为布局创建 attempt/runtime，确认快照由协调者按执行门禁管理。

## 2. 围绕需求核查现有实现

对相关仓库做有边界的只读调研。优先定向搜索，并行读取独立材料，避免无界扫描、重复调研或反复猜测不存在的路径。

先检查仓库指令、当前分支、修订和未提交改动，记录分析基线。没有 Git 或材料不完整时如实说明；本地分支不代表生产版本或后续开发基线。

按相关性追踪入口、调用链、数据结构、业务层、SDK、持久化、鉴权和前端交互。区分需要修改、仅作依据以及其他团队负责的组件。

重点核查：

- 已有能力能否复用，包括通用转发、请求封装、错误响应、版本更新及资源初始化。
- 字段和身份如何跨组件传递，可信身份来自何处，权限及环境边界在哪里。
- 真实入站路径与下游身份方向分别核实；复用关键 helper 前检查正常和默认/降级分支，不由名称或旧候选架构推断其行为。
- 业务校验、格式校验、环境归属和账号存在性各自的语义，不能相互替代。
- 失败和并发时的真实行为，如条件更新是否检查匹配数量、原子性由何种机制保证。
- 配置保存、下发及实际生效的时机，存量资源和旧客户端如何处理。
- 实际 handler、默认中间件/编码器与消费者如何处理正常、无结果/空值及错误信封；DTO 或 Mock 返回一致不能证明真实传输合同成立。

区分“代码已核实”“用户已明确的系统能力”“待联调验证”，为结论保留代码位置、修订或材料依据。代码中存在配置不代表生产链路已经启用；无法验证的行为保留为待核实。

自行核查实现事实，仅在核查结果影响业务选择或验收口径时直接向用户澄清，并将结论写回同一份 `requirement.md`。沿用已足够的错误处理和查询能力，不将普通实现问题默认扩展为新的用户状态、恢复流程或额外报告。

默认不修改业务代码、不切换分支、不运行会变更依赖或生产数据的命令。优先复用已验证能力；确需增加仓库、协议或基础设施时，先说明原因、证据和最小改动，请用户确认新增范围，同时继续完成独立部分。

## 3. 按标准模板形成整体方案

编写前读取本 Skill 的 [assets/design_template.md](assets/design_template.md)，以它作为标准模板，按“背景与目标、当前现状、整体方案、模块改动、关键取舍与影响、实施与验证、评审事项”的顺序组织正文，参考与详细材料按需放在附录。

用户指定历史方案时，实际读取具有代表性的两到三份（可用材料不足时说明）。参考表达方式、图示和评审习惯，在标准模板内组织内容；不复制其他需求的业务结论、架构或功能。用户明确要求调整模板或结构时遵循用户要求。

输出文件名保持 `design.md`，版本记录在文件内，已有方案沿用原位置及版本记录。使用模板的标题及元信息，注明需求文档链接和确认版本、作者、更新日期与方案版本；状态如实使用 `待评审 / 修订中 / 待确认 / 已确认`，不能编造作者或确认信息。

先讲清整体方案，再展开实际模块改动与选择依据。正文保留影响评审结论的设计、接口边界和风险；完整接口定义、长代码、详细测试和 SOP 按需链接。提交评审前删除填写提示、占位内容和不适用内容，不为填满模板新增工作。

以最小必要改动满足需求。正常、异常、边界与配置生效规则应连贯呈现；需要时使用架构图、流程图或时序图，图文的字段、状态和失败结果必须一致。

## 4. 编写组件契约和验收 Case

按业务组件组织改动，解释“改什么、为什么、如何运作、出现异常怎么办”，不能只列文件名。核心逻辑集中，同语义命名一致。使用稳定组件编号（如 C1）关联需求编号（如 R1），映射较多时移至附录。

在标准模板对应章节内按实际需求展开：

| 模板章节 | 应说明的信息 |
|---|---|
| 1. 背景与目标 | 当前问题、预期结果、本次范围与既有约束，完整业务规则引用需求文档 |
| 2. 当前现状 | 当前链路、已有可复用能力及缺口，影响方案判断的事实附依据，未核实内容标明待核实 |
| 3. 整体方案 | 推荐方案、核心变化、模块职责与关键流程，区分保存、返回和实际生效 |
| 4. 模块改动 | 按模块或仓库说明数据或接口变化、核心处理及关键边界；关键字段、默认值、校验、错误、权限、并发和上下游契约在所属模块内定义 |
| 5. 关键取舍与影响 | 选择依据、实质性备选、存量兼容及可靠性、权限或性能影响，区分已验证和待验证的成立条件 |
| 6. 实施与验证 | 改造范围与真实依赖、外部对接和联调责任、具体验证重点、必要发布顺序、启用条件与回退限制 |
| 7. 评审事项 | 确实待决定或待验证的事项、当前建议及影响、真实评审结论；保留实际确认版本、确认人及日期，未确认时填写“待确认” |
| 附录（按需） | 代码与调研依据、详细接口或子模块方案、完整测试与报告、已有执行计划、SOP、修订及评审历史 |

同一契约集中定义，其他章节引用，避免字段、响应结构、错误语义或时间规则出现多个版本。代码和 JSON 示例应与最终契约一致。

测试使用稳定编号（如 V1），覆盖实际涉及的正常、异常、边界、并发、权限、环境隔离、兼容和跨组件验收。第 6 节保留影响方案判断的核心、边界及联调验证重点，写清对应需求、前置、操作和预期结果，不能只写“测试接口成功”。完整用例与 R / C / V 映射较多时可放在附录或链接材料，不强制另设正文目录。明确区分计划验证和已运行验证。

涉及跨仓库合同，在第 6 节明确生产者真实入口、默认编码器和实际消费者的验证责任，包含相关正常、空值和错误响应；数据库原子性使用隔离真实存储，前端交互按需经过实际浏览器。写明 Mock 边界、工具链/框架/时区和与目标环境的差异；不能将局部 Mock 或只编译作为真实验收。验证计划与 [integration-validation](../integration-validation/SKILL.md) 衔接，运行和证据按 [共享约定](../delivery-flow/references/validation-and-evidence.md)。

真实依赖写入第 6 节的改造范围与依赖，明确下游可消费的固定版本/产物、获取条件及解析验证，不能仅写本地 commit 或浮动源码路径。上线和回退写入对应小节；涉及混合版本、数据迁移或外部资源时说明回退限制，详细操作按需链接 SOP。不把普通仓库发版凑成外部依赖，不保留不适用的空壳或重复免责声明。

## 5. 准备必要的外部对接材料

仅在涉及其他团队时生成，沿用已授权命名与位置，说明职责、调用方式、接口契约、异常处理、联调条件和验收标准。与需求及方案共用同一版本的契约，不额外扩大对方工作范围。

准备材料可以在授权范围内继续完成；发送消息、邮件或提单须有明确授权及可确定的接收目标。

## 6. 处理评审反馈与版本迭代

收到反馈后直接更新已授权的文档，先区分业务规则、技术选择、仓库范围和文档组织方式的变化。

- 用户给出接入方式或范围结论时，将其作为约束继续核查，清理被否决方案的接口、关联改动、测试和发布步骤。
- 用户调整写作方式时，按实际内容重组章节，保留已确认技术契约。
- 业务语义或验收变化时，写回需求正文并标明受影响确认状态；需要时返回需求澄清。
- 同步需求、方案、外部对接材料及版本引用，不能只追加一段结论而保留旧方案矛盾。
- 更新版本、真实 Review 和变更记录；未核实事项保持待验证，不将文档修改描述为方案通过。

第 7 节的当前评审事项只保留未解决事项，已确认结论写回所属正文并在附录按需保留评审历史。整稿确认记录始终保留，注明实际确认版本、确认人、日期及依据；局部事项的结论不替代整稿确认。

本 Skill 不创建或修改 `delivery.json`；整体状态由 `delivery-flow` 协调者从初始化开始管理，并同步文档中的真实确认。方案未确认前不生成执行计划或控制目录。已有交付记录及执行快照需要变更时，遵守工作区流程同步确认基线及受影响材料，不直接修改活跃执行状态。

## 7. 检查与交付

交付前检查：

- 需求基线、用户已确认结论和最终方案一致，旧假设已清理。
- 字段、接口、状态、时间、错误语义及各文档契约一致。
- 原子性、可信身份、兼容和环境边界有事实依据或明确待核实。
- 组件改动解释充分，Case 覆盖关键需求，计划验证与已运行验证分开。
- 模板元信息、需求确认版本、方案版本、链接、代码位置及示例正确，文档状态和第 7 节确认记录有真实依据。
- 结构遵循自带模板或用户明确调整，填写提示、占位内容及不适用内容已删除；正文保留关键设计与风险，详细材料按需链接，无重复段落或额外引入的工作。

执行适当的文档内容与一致性检查，并遵守工作区要求的验证；不为文档整理新增业务测试或宣称通过业务验收。

交付可点击的方案及必要对接材料入口，简述变化、验证结果和未解决事项。只有缺少真实阶段确认时，才请用户评审具体版本。可以交付完整“待评审”稿，不得称为已审批方案；确认后交接技术方案基线，后续执行准备按另行授权和工作区流程处理。恢复旧方案时沿用已有真实确认和版本记录，不因模板更新重建文档或执行状态。

## 调用示例
