# 来源材料管理

供协调者、需求分析和技术设计共用。`sources/` 是本工具包在需求目录内定义的输入存档约定，不是 Agent Skills 标准目录，也不保存业务源码、执行状态或批准快照。按需创建，沿用旧需求已有来源入口，不强制迁移或回填。

## 1. 区分来源与当前基线

用户提供的需求说明、旧需求文档、预调研方案、接口规范、交互稿和附件均先识别为输入。标题包含“需求”“方案”、正文写着“已评审”或记忆中已有旧任务，不证明它们属于当前交付或已获本次批准。

协调者先按 delivery-flow 核验当前需求目录及交付记录，再决定新建、恢复或显式采用旧基线。新建需求仍从 requirement-analysis 开始；来源的读取、存档和技术事实核查不能跳过需求与方案确认。正文中的需求、建议、历史结论和本次确认分别表达。

采用旧文档时记录确切版本和本次采用范围，原文作为来源保留。只有同一交付的有效确认，或用户明确覆盖该版本的本次确认，才能成为当前批准依据；来源记录和原文中的评审字样不代替确认记录。

## 2. 何时收录

将“登记来源”和“保存原文副本”分开判断。在第一次据材料形成结论或交接前完成必要登记；读取失败也如实登记，不先编造正文。

| 情况 | 登记与保留方式 |
|---|---|
| 用户提供的材料用于确定问题、范围、业务规则、技术契约、约束或验收 | 必须登记出处、版本/读取时间、用途和实际读取范围；按第 3 节判断是否需要本地原文 |
| 用户给出的关键澄清、纠正或局部/整稿确认 | 有效结论和确认仍写所属文档；仅聊天可见且后续需要追溯时，收录相关原话及日期/消息定位，不复制整段会话或个人记忆 |
| 用户明确要求保留、归档或后续 Agent 需要但可能无法重新访问的材料 | 在授权需求位置保存必要正文/导出或附件，并在索引记录来源和读取限制 |
| 来源有冲突、被替代或方案被否决，但用于解释已作决定或验收差异 | 保留支持决定的对应版本或必要摘录，标明采用/未采用及理由；不将旧建议留作当前规则 |
| 关键来源尚未读取、读取失败或只拿到部分内容 | 登记真实状态、缺失范围和影响；不能把搜索摘要、页面 HTML 壳或目录链接标为正文已读取 |
| Agent 自行查到的官方规范等，实际用于关键结论 | 按同一标准登记；不将所有搜索命中和无关资料收录 |
| 仅作背景、表达风格参考，且未影响规则或决定 | 当前文档注明引用及用途即可；没有独立保留需要时不创建 sources |
| 仓库源码、固定模块、构建产物、运行日志或验证截图 | 在方案、Review 或验证入口记录确切修订与证据，按产物管理保存；不复制一套到 sources |

只有口头需求且已经完整写入 requirement.md 的简单场景，无额外原文追溯需要时可直接在其输入来源中注明“本会话用户输入”。有独立来源需登记或保留时再创建 `sources/index.md`；不为目录完整性创建空索引。

## 3. 保存什么，放在哪里

默认位置为 `<DELIVERY_DIR>/sources/`，不放到工具包公共 sources 或业务仓库。只保存与当前交付相关且已授权读取的材料；来源原文件保留原位置，不修改或移动它。

优先引用已存在、可按固定版本获取的原文，记录获取路径与限制。下列情况需要保存本地材料：用户明确要求存档；附件/截图/粘贴原文是唯一输入；远端可能变化且不能按原 revision 重取；后续执行者无法可靠获取本次采用内容；冲突和决定需保留当时原文。需要保留原文而暂时无法取得时记录缺口，不能以链接或摘要冒充已存副本。

正文完整导出可取得且后续需要独立复核时，保存该版本正文；只需某几节且原文可固定获取时，可以保存必要摘录并注明章节。摘录、OCR、转写和 Agent 摘要分别标注，摘要不能替代需要核查的原文。评论、表格、画板、附件或外链影响结论时，单独获取对应材料；正文导出不含它们就记录未读取/未保存范围。

建议布局：

```text
sources/
├── index.md                         # 当前交付的来源索引
├── S01-feature-brief-r7.md           # 在线正文导出；标明导出格式
├── S01-r7-assets/flow.svg            # 实际影响规则的画板/附件
├── S02-api-contract-r3.pdf          # 用户提供的原附件，保留格式
└── S03-clarification-read-20261109.md # 必要用户原话及定位
```

来源 ID 默认 `S01`、`S02`，按本需求已有索引分配，唯一且稳定；旧 ID 不改名。文件名包含 ID、简短用途和实际版本键；版本未知时使用读取日期，必要时加内容摘要短前缀避免同日碰撞，不编造 revision。名称是安全的单一路径段，校验目录、同名内容及符号链接边界，不能将文档标题或 URL 直接拼成路径。

同一来源的同一内容复用已有文件；原文变化时增加对应版本文件和索引记录，不覆盖已用于确认、决定或验收的旧版本。必要资产跟随其来源版本引用，不混用新正文和旧附件。正文摘要可以继续修订，已冻结原文不随摘要修改。

`sources/index.md` 是来源详情入口，每项至少说明：

| 信息 | 要求 |
|---|---|
| 稳定 ID、标题与来源性质 | 区分用户原始业务输入、参考需求、参考方案、协议规范、附件或澄清；性质不是批准状态 |
| 原始出处与提供方式 | 安全的 URL、文件位置或消息定位；用户提供/Agent 检索，以及真实接收或读取时间 |
| 本次用途 | 支持的需求名称或已有编号、方案章节或决定；未采用时说明原因 |
| 版本与读取状态 | 已知 revision/版本/固定 commit；未知则注明未知及读取时间；已读取/部分读取/未读取/读取失败 |
| 实际读取范围与限制 | 正文/具体章节、表格、评论、附件、外链；未读部分及其影响，不能把“已下载”当作“已核查” |
| 本地保存与可再获取性 | 对应文件链接、原附件/正文导出/摘录/转写的类型、固定版本获取方法或限制；未复制时注明只引用原文及理由 |
| 内容身份 | 已保存文件的 SHA-256 或平台可核实的版本标识；哈希只证明保存内容，不能证明读取完整或已批准 |

以可读的来源名称组织小节，在条目内记录稳定 ID；按本轮确切版本更新用途和读取状态，历史版本留在该项内。信息集中在索引，不为每个来源再建 metadata.json 或独立报告。不能可靠跳转到条目时，链接索引文件并用文字说明来源名称及版本，不强制增加锚点。

requirement.md 和 design.md 只保留便于阅读的出处、用途和来源索引链接；关键依据用来源名称、版本及章节定位，稳定 ID 可用于记录关联，不能只写未解释的代号。design.md 的来源入口及历史用途按 [technical-design 的文档组织约定](../../technical-design/SKILL.md#3-按标准模板形成一份技术方案) 收在文末维护区，正文在相关结论处引用必要依据。不要复制多份来源状态表。协调者在 `delivery.json.sources[]` 中用可选 `id` 和 `index` 关联索引，例如：

```json
{"id":"S01","index":"sources/index.md"}
```

这只是协调文档约定，不是 CLI 必填 schema。已有 sources 中的 url/path/revision 等字段及未知字段保留，兼容引用；没有来源索引的旧需求可继续使用。新增索引时引用旧出处，不为套模板批量迁移或改写活跃记录。

## 4. 谁维护，如何交接

mainAgent 决定收录范围并分配唯一 writer；默认维护索引与 `delivery.json.sources[]`。需求/设计执行者默认写各自人工评审文档，返回所用来源和缺口；只有获分配来源路径时才写正文/附件或索引的指定范围。所有 sources 写入仍在当前授权需求位置，不能因读取了资料获得其他仓库写入权。

来源登记或内容更新不改变 `delivery.json.status`、documents.confirmed_version 或 approvals；实际批准继续由所属阶段文档和协调者记录。参考方案转换为当前方案时，新方案版本及状态独立维护。

交接前核对来源链接、版本、读取范围、必要副本和内容身份是否一致，让下一位执行者能区分已经核实、尚未读取、未采用以及当前批准的材料。control 内保存原文快照，不改写已批准正文；其中的相对引用应按原文所在目录理解，预览器从 control 直接打开时可能无法跳转。在 execution.md 和委派输入中提供原文目录及可解析的来源索引绝对路径，不假设 control/sources 存在或重复复制原文，也不将路径存在检查写成导航验证通过。

访问失败只影响依赖该资料的结论，独立部分继续；替代读取方式仍需满足同一范围及证据要求，不能凭工具成功、切换身份或猜测正文冒充补齐。

不保存 token、凭据、带签名的访问参数、无关生产数据或整份私人聊天；必要出处去除秘密参数并注明安全获取方式。来源材料位于被忽略的需求目录，不能复制到公开 Skills、模板或示例。阶段结束不自动删除旧来源或必要原文证据。
