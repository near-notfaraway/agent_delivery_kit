# 单仓编码任务执行

供通用编码 subAgent、独立仓库会话及串行执行者使用。协调者按 `agent-delegation.md` 提供调用输入；本文件负责编码执行步骤，不要求自定义编码 Agent，也不授予整体协调权。

没有子 Agent 能力时，mainAgent 可按本文件兼任编码执行者，仍以真实 owner 逐任务认领/恢复和交接；整体协调继续按 delivery-flow 执行，评审遵循委派约定的自检与独立审查边界。不伪造子会话，也不因串行执行绕过任务状态或授权。

## 1. 恢复任务与固定输入

读取本项目及目标仓库适用指令、委派范围、确认需求/方案和 `control/execution.md`。旧控制目录缺少执行说明时沿用已有基线和记录，不为恢复重建控制面。

核对唯一授权 worktree、基线、实际分支/HEAD、未提交修改及 writer。运行：

```bash
"$COORD" context --project "$PROJECT" --task "$TASK_ID"
```

随后读取 `delivery.json` 当前交付修订、corrections 和有效批准决策；历史 handoff 不自动包含后续修复。按固定版本核对上游依赖及其获取/解析证据，不从浮动 HEAD 推断交付。

以上变量均来自真实调用输入，路径使用绝对路径并正确引用。检查每条命令的退出码；不发明 CLI 命令或绕过依赖。

## 2. 确定新任务或续接

- `pending` 新任务先执行下述 claim，只有成功后才能修改业务代码。
- `claimed` 恢复任务先核对持久 owner 和旧 writer 已停止，续接同一 owner；不再次 claim，也不另起 owner 强抢。
- `completed` 任务的修复按 `recovery-and-corrections.md` 处理，默认复用原需求 worktree，保留原 `result`，不重新 claim/complete。
- 非本次范围、依赖未满足、来源或 writer 无法确认时返回具体阻塞，不自行换仓库、分支或任务。

```bash
"$COORD" claim --project "$PROJECT" --task "$TASK_ID" --owner "$OWNER"
```

CLI 没有租约、超时回收或重分配命令。同 owner 重复 claim 也会失败；失败或工具中断先核对实际持久状态，再只补未完成步骤。

## 3. 实现与验证

### 编码前：核实链路与最小范围

对照确认方案及其分析修订核实实际代码，不把方案中的假设当作已有保障。复用 [technical-design 的现有实现核查](../../technical-design/SKILL.md)，在已有执行或评审入口简要保留以下结论及代码依据，不另建一套材料：

- 需求涉及的完整原路径：入口、校验、业务编排、事务保存、消息及重试/重放、配置下发、生效和资源释放；每步由谁负责、读写什么数据及版本、实现在何处。不涉及的环节不强行补造。
- 调用方、服务端契约、默认解析及已有 SDK 能力；未知字段、空值和错误的现有行为，以及新增限制的需求依据。
- 已有锁、事务、重试及回滚的实际覆盖范围、所有者和释放时机，区分已证实缺口与待核实风险。
- 当前任务必改模块、外部行为及可复用扩展点，明确顺序调整和字段传递能否满足需求，再确定最小改动清单。

能够自行核实的内容在编码前完成。新事实推翻方案前提时先修正受影响设计，不以新增专用流程维持旧假设；涉及已确认方案变化时按下述偏离流程返回 mainAgent。

### 实现中：核实新增机制的必要性

在唯一授权仓库按 acceptance、确认方案和有效决策实施最小改动。每次准备新增接口、锁、ctx 业务数据、结果存储、元数据回读或事务单元时，先回答“现有能力为何无法承担”：指出具体缺口、代码或运行证据，以及为何不能通过复用、顺序调整或完整传参解决。不能回答时先核实并收敛设计，不因假设性风险增加机制；必要依据写在已有实现说明中。

按所需数据版本安排读写时机。业务编排层负责顺序，消息及重试/重放明确携带所需字段，Model 保持元数据读写职责。旧值或缺字段出现时先查读取过早、传递遗漏和版本选择，不默认用 ctx 覆盖配置、整体重载或回读补齐。发现旧假设不成立时检查所有依赖它的调用、数据结构和测试，同步删除或修正失去依据的机制及断言，再继续实现。

行为变化先从需求和外部行为推导一个失败行为测试并确认失败，再最小实现并运行必要完整检查。重点验证相关配置使用正确版本、字段完整传递、原流程兼容及非目标环境保持原行为，不把新增 ctx、回读或覆盖方式本身当作业务预期。涉及所有权、状态、决策或持久化时补并发验证。低影响文档修改不机械新增测试。

按 `validation-and-evidence.md` 核查初始化、TestMain、脚本、工具链、依赖、外部目标与隔离条件后运行验证。保留真实失败和未运行范围，冻结最终源码、差异、依赖、配置与结果；不能为错误的测试夹具改动正确业务逻辑。

读取 [产物管理](artifact-management.md)，使用分配的当前证据、attempt 和 runtime。必要运行脚本、测试副本、缓存及普通探测输出放 runtime；attempt 仅保存支撑结论的关键失败、最终结果及必要身份。每次尝试结束完成筛选、引用核查和自有临时资源处理，再交回评审；仍需使用的资源记录保留条件，用户明确暂不清理时如实记录未处理。已有仓库工具优先复用，不每轮另造 freeze 或记录脚本，不把完整运行环境默认归入长期证据。

按需读取本次范围内的其他 Skills。Skill 不扩大修改或发布授权；业务选择、跨仓库合同变化和验收缺口返回 mainAgent。需记录偏离时按委派安排执行 `decide` 或交由 mainAgent 记录，需审批的变化在确认前暂停受影响部分。

## 4. 交给协调者评审

### 交付前：由实现者完成自查

交审前检查 staged、unstaged 和相关未跟踪文件的完整差异，并核对任务累计差异；不只检查最近修改的文件。逐项确认改动有需求或有效决策依据、职责放置正确、新增机制仍有必要、关联测试验证业务结果。清理自己引入的无关改动，保留其他 writer 的已有工作；顺带改变指标口径等额外改进须从本次差异中恢复，或按独立范围获得授权并单独验证，不混入需求交付。无法恢复或仍未解决的事项明确列出，不以测试通过代替处理。

链路、机制必要性、分层职责、范围和断言的核实由实现者承担，不能等待用户逐段指出。自查结论写入已有评审或验证入口，区分单测、只编译与真实联调的成功、失败及未验证项；检查通过后仍复核设计是否因实现事实而需要收敛。

实现和必要验证就绪后，按产物管理检查材料完整性并返回实际差异、冻结摘要、验证与下游交接材料，以及新增材料和遗留资源。mainAgent 按 [delivery-review](../../delivery-review/SKILL.md) 核验或委派评审，再按其第 4 节组织用户概览，明确本次完整范围的改动、解决的问题和主要代码；不能仅展示最后一次修复或冻结记录。材料就绪立即单独向用户展示本任务，不等待其他独立任务。编码者只修复返回的问题，不自行派生 Reviewer 或把自检称为独立审查。

缺少覆盖本次差异的提交授权时保持 `claimed` 和原 owner。等待授权不是任务完成，也不需要重新认领；沿用已经明确覆盖的授权，不由方案确认或另一任务批准推导提交权限。

准备接口/数据合同、固定依赖版本或产物及下游实际获取/解析证据。提交尚未形成时先交付冻结内容和可行获取方式；真实提交形成后补齐最终固定输入，不用浮动源码路径作为最终交接。

## 5. 授权提交与完成交接

mainAgent 确认本次验收和有效授权满足后，当前 writer 按仓库与宿主 Git 规范创建新增 commit，核对完整 SHA、父提交、源 blob 与被批准的冻结差异一致。变化影响证据时重验相关范围；仅提交或路径变化可在证明等价后复用证据。

`--validation` 包含当前 Review/验证摘要与入口，`--handoff` 包含下游合同、确切固定版本/产物、获取验证、兼容与集成方法。新任务在仍为 `claimed` 且 owner 正确时执行：

```bash
"$COORD" complete --project "$PROJECT" --task "$TASK_ID" --owner "$OWNER" \
  --commit "$COMMIT" --validation "$VALIDATION" --handoff "$HANDOFF"
```

检查实际结果并立即通知 mainAgent。由 mainAgent 核验、同步当前交付指针并读取 summary 调度下游；Git commit 本身不解锁依赖。修复不执行上面的 complete，返回真实新提交及修复证据，由 mainAgent 更新 correction 和当前交付指针。

工具部分失败按恢复约定核对真实副作用，成功提交或 complete 不重放，不改写活跃控制文件。返回前按产物管理完成证据及资源交接核查，报告实际处理与遗留条件。
