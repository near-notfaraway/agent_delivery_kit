# 交付产物与临时资源管理

供 mainAgent、阶段 Skills 和所有执行者共用。这里只定义产物位置、保留和资源生命周期，不新增 CLI 命令、任务状态或持久化协议。按实际阶段生成材料，不提前创建空目录或整套模板。

## 1. 创建前先分类

写入前确认用途、唯一 writer、已有入口及保留条件，优先更新或引用现有材料。非标准产物确有必要时，在已有执行/验证入口说明用途和位置；授权范围内的可逆材料选择不逐文件请求用户批准。新增业务范围、发布或破坏性操作仍遵循实际授权。

| 类别 | 默认位置与产物 | 创建及保留规则 |
|---|---|---|
| 当前人工评审文档 | 需求根目录的 `requirement.md`、`design.md` | 各阶段维护固定入口，版本与历史遵循所属模板；需求分析仍只输出一份 requirement.md |
| 整体状态与阶段交付 | 根目录 `delivery.json`、最终 `delivery-report.md` | mainAgent 维护；任务结果仍由 CLI 管理，不额外维护第二份实时状态清单 |
| 执行控制与确认基线 | `control/` 的快照、execution.md、project.json、decisions.jsonl、baselines/、bin/coordctl 及实际锁文件 | 遵循原确认门禁；持久记录、基线和活跃二进制不是临时资源 |
| 正式业务工作区 | `repos/<仓库别名>/` | 保留真实基线和修改；Git 元数据及支撑该 worktree 的镜像按仓库准备规则管理 |
| 按需来源与对接材料 | `sources/` 及已约定的对接文档位置 | 只保存必要来源和实际要求的材料；用户要求的复盘可沿用指定文件，不作为所有需求的标配 |
| 当前证据入口 | `reviews/<scope>.md`、`validation/<scope>.md`；准备/集成使用 preparation.md / integration.md | scope 为任务或独立修复身份；一个范围保留一个当前入口，正文显示当前结论 |
| 历史证据 | `validation/attempts/<scope>/<attempt>/` | 按实际尝试保存必要日志、差异、摘要、结果、截图和回执；当前入口链接其用途及修订 |
| 固定可消费产物 | `validation/artifacts/<产物名称>/<固定版本>/` | 本地模块包等在下游仍使用或需要复核时保留；来源、摘要和获取证据放现有验证入口 |
| 可重建运行资源 | `.runtime/<scope>/<attempt>/` | 临时脚本、源码副本、测试二进制、预览工程、空下载缓存、数据库数据目录等；按第 4 节处理 |

这是默认布局，不要求迁移已有需求。保留旧目录、链接、确认、原任务 result 和证据；恢复时在现有入口说明当前来源。旧运行目录不得因位于 validation/ 就自动视为永久证据，也不得未经核查直接清理。

需求根目录不堆放一次性 update、record、freeze 脚本或中间 JSON 载荷。工具自身生成的锁文件不属于杂乱产物，不为整理目录删除仍可能被使用的锁。

## 2. 分配位置与组织尝试

mainAgent 在开始有运行或历史证据需求的工作前，分配 scope、稳定 attempt ID、当前证据入口、历史目录、runtime 目录、可写范围及 writer。只做文档分析时不要求 attempt 或 runtime，不为补齐输入创建额外产物。

scope/attempt 的目录键必须是安全的单一名称，不含空值、`.`、`..`、路径分隔符或目录逃逸；不要直接拼接未经校验的任务 ID。创建或清理前核对实际解析路径及已有链接，确认位于授权位置，不经符号链接误写或清理其他资源。

attempt 使用范围内可识别且不冲突的编号，如 `001`；新尝试前检查已有目录与内容。重试同一次未完成操作继续原 attempt，先核对真实副作用；源码、依赖、配置变化或需保留独立失败/复验结果时创建新 attempt 并关联前次，不用 `final-2` 等名称建立竞争入口。

同一 attempt 可集中保存命令及结果，如一份 commands.log 或结构化日志，必须能定位每条命令、目录、运行条件、退出码和时间。需要独立截图、响应或故障日志时按用途保存，不机械要求每个测试步骤各有报告、脚本和 SHA 文件。

当前入口正文只展示有效结论、固定修订与待办，历史描述放历史部分并链接对应 attempt。多个 attempt 合并支持验收时，说明各自覆盖的 Case、源码/配置等价依据和总覆盖；不能把部分复验描述为重新运行全套。

证据至少保留关键失败、最终通过、必要源码/依赖/配置身份、实际批准和下游获取依据。失败处理、例外或业务修复所依据的证据不能因“过期”丢弃。工具尾部报错与业务动作结果分开保存。

## 3. 控制复制、冻结与脚本数量

- 已提交源码优先引用固定 commit 和获取方式；未提交内容保存必要 diff、文件摘要及相关依赖/配置身份。运行需完整副本时放 runtime，不默认把整个仓库、第三方依赖或无关大文件复制到每轮长期证据。
- 下游尚需本地产物时集中保留一份固定版本包和摘要，空下载缓存属于 runtime。推送源码不等于远端模块获取已验证；替换本地分发前先证明新的获取路径成立。
- 已确认基线按内容摘要检查重复：相同内容可引用已有不可覆盖快照，将新的真实确认依据写入现有基线索引；新内容才保存新快照。当前控制快照仍按流程同步，不生成相同内容的 before、copy 或备份副本来代替确认记录。
- 同一冻结材料不默认同时长期保留展开目录和压缩包。必要日志、文件和产物被 manifest 引用时，先明确哪些必须保留；证据摘要和重建命令不能代替验收要求的实际产物或证明。
- manifest 如确有必要，每次尝试保存一份固定证据索引并标明修订和覆盖，当前入口引用它。更新当前文档不要求复制一套历史 manifest，不以重命名方式产生多个“最终”索引；历史索引不改写成新的验证事实。
- 创建辅助脚本前先检查本仓库、需求和业务仓库是否已有可用能力。一次性脚本放 runtime，来源、用途和必要重建命令留在现有入口；清理前判断脚本是否仍是复验所需材料。
- 修改交付状态的脚本必须遵循锁、原子替换、未知字段保留与稳定事件身份去重。只完成原子写但重复追加批准或阶段历史的脚本，不可作为标准重试入口；按恢复规则核对状态后仅补缺失项。

不以文件数量上限代替判断，也不为减少文件省略必要验证。完整产物不能再获取、属于必须复核的证据或确需保留运行现场时，在当前入口说明原因、归属、后续条件及位置，不强行清理。

## 4. 临时资源生命周期

创建临时进程、数据库、目录、缓存或端口前，在已有验证入口或本 attempt 的必要记录中注明：用途、实际 owner、资源身份/绝对路径、目标范围、关联 attempt、停止与清理方法、预期保留条件。不能只凭 `.runtime` 名称判定目录归属或删除权限。

按实际工具结果记录 PID/启动身份、监听目标和创建出的资源。若创建部分成功或执行中断，先恢复这些事实，保留失败证据，不重复启动或重复写数据。无法证明归属时返回 mainAgent，不能停止他人进程或尝试盲目删除。

尝试结束，包括失败或取消时：

1. 保存支持结论的必要证据到历史目录，核对内容、摘要、链接及读取方式；若日志/manifest 仍引用待清理产物，先保留需要的产物或记录经核实的归档关系，不能留下断链。
2. 停止本次自有服务，核验实际退出和必要监听状态；停止结果与测试退出码分别记录。不能由 cleanup 总退出码推断所有清理动作已成功。
3. 确认数据库、预览目录、二进制或缓存不再被 writer、下游或复验使用后，按本次授权和已记录归属处理自有临时资源；目录删除后核验实际不存在。正式 worktree、支撑镜像、持久控制记录和业务数据不进入这一清理流程。
4. 分别报告“进程已停止”“临时目录已删除”“产物仍需保留”或“清理失败/未执行”。遗留给出位置、用途、占用者或归属、原因及后续处理条件，不把仅停止服务写成数据库已清理。
5. 清理异常保留事实并交回 mainAgent，继续独立可执行工作。明确且有理由的资源保留不是验收失败；未解决安全占用、必需证据丢失或未完成的验收仍阻塞对应范围。

阶段结束不自动授权删除历史需求材料或正式 worktree。迁移或清理旧需求另按实际授权处理，不重写原验收事实。

## 5. 交接材料核查

执行者返回前、Reviewer 形成结论及 mainAgent 推进交接前，核查相关范围：

- 当前入口唯一且版本/结论明确，历史尝试已标明覆盖和来源，没有第二份竞争的当前状态。
- 证据对应实际最终源码、依赖与配置，必要失败、最终结果及批准依据可读取；日志、manifest 和链接无遗漏或断链。
- 新增非标准材料有用途，运行资源按类保存，正式支撑资源与可重建资源区分清楚。
- 停止、删除、保留与失败有真实结果，遗留及复验所需资源有责任和处理条件。

将核查结论及新增材料/遗留资源简述在现有 Review、验证或返回结果中，不新建一份“目录清洁报告”。材料缺陷由相应 writer 修正；缺少必需证据或存在 writer 冲突时暂停受影响交接，不因整理目录停止其他独立任务。
