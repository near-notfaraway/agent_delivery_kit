# 当前交付修订、恢复与返工

以下是协调者的记录约定，不新增 CLI 命令或 version 1 任务状态。已有 `project.json`、任务 `result` 和 `decisions.jsonl` 的语义保持不变。

## 1. 历史任务与当前交付

`project.json.tasks[].result.commit` 是任务首次完成时的不可变事实；后续修复不覆盖 `result`、不重新 `claim` / `complete`、不伪造 `reopen`。

`delivery.json.repositories[].delivery_commit` 是该仓库当前已评审、获对应授权并完成提交的交付修订，由协调者唯一维护。首次完成或修复提交后核验真实 commit 与证据，再更新此指针。不存在该字段的旧交付记录仍可使用：读取相关已完成任务的 `result.commit`，必要时核对已经存在的修复证据后由协调者补录，不能由浮动 HEAD 猜测。

同仓库多任务时按真实依赖和提交历史确定包含已交付内容的修订；提交不能证明包含全部应交付改动时先核查，不盲目取时间最晚者。未提交或未获范围授权的修复不能进入当前交付指针。

旧 `commit`、`baseline_commit`、历史记录等字段保留原语义。其他修订清单或报告只从当前指针派生，注明来源，不维护第二个权威字段。若旧需求已有其他当前指针字段，核对其真实证据与新字段一致后兼容读取；不静默删改旧字段或重建状态。

可选记录字段如下，均属于 `delivery.json`，不写入 version 1 任务图：

| 位置 | 字段及语义 |
|---|---|
| `repositories[]` | `delivery_commit` 完整 SHA；`delivery_review` / `delivery_validation` 为该修订的证据入口 |
| `corrections[]` | 稳定 `id`、`task_id`、`repo`、`owner`、`original_task_commit`、`parent_commit`、`commit`、`review`、`validation`、`approval_id`、`affected_task_ids`、`at` |
| `approvals[]` | 结构按 delivery-flow 第 3 节；修复确认通过 `correction_id` 关联，不生成第二套批准字段 |

首次完成的指针不需要伪造 correction。修复记录可以先保存原因和范围，尚未形成的提交/批准字段保持 null；真实完成后补齐同一 `id`。`approval_id` 只引用实际存在且覆盖范围的确认，不能生成批准事实。

每次下游恢复、集成或发布准备，在 CLI `context` 之后还须读取当前交付指针、corrections 和有效批准决策。CLI context 继续返回历史任务证据，不保证自动包含后续修复；上游合同变化时核查并记录受影响下游的复验范围。

## 2. 已完成任务的修复

1. 记录原任务、失败证据、修复原因、合同和下游影响。确认仍在已授权需求范围内；行为或验收变化按设计偏离流程处理。
2. 默认复用原需求分支/worktree。检查真实源、记录基线、分支/HEAD、未提交改动、唯一写入者和活跃验证占用。旧写入者停止后续接原工作，不为保护历史 result 冻结正常迭代。
3. 只有确有并发、基线或隔离需要时另建工作区，并保存其与原需求修订的关系；不另建临时修复分支作为默认流程。
4. 实现、交付评审、验证和提交授权仍按本修复的实际范围推进；旧任务批准不自动覆盖新差异。无任务图变化的修复不默认升级为任务图维护。
5. 新增真实 commit，核验父提交、冻结内容和证据，更新同一 correction 记录及 `delivery_commit`。保留原任务 `result`。
6. 立即读取 `summary` 并核查受影响下游；仍未完成的可执行任务继续调度，已完成下游不重新 claim，以必要复验及修复证据维护。修改依赖或任务边界确有必要时另走安全计划维护，不能手改活跃任务图。

问题未解决或必需复验未完成时不能宣称整体完成；若原整体已完成，记录真实状态变化与恢复原因，再进入相应开发或验证阶段，不改写历史完成记录。

## 3. 部分成功后的恢复

恢复先读取实际状态，再决定下一步：

| 对象 | 要核对的事实 | 恢复方式 |
|---|---|---|
| Git | HEAD、父提交、最终文件、status、worktree 注册与分支 | commit/worktree 已成功则只补缺失记录，不重复创建；未完成才按真实授权继续 |
| 远端推送 | 已验收 commit、目标 remote/ref、实际远端 SHA、已有逐仓结果 | 远端已是目标 SHA 时保留成功，只补缺失核验/记录；失败项按原授权继续普通推送，不回滚成功仓库或 force push |
| CLI | task status、owner、result、summary、决策 ID 与内容 | claim/complete/decide 已成功则不重放，补齐协调记录或调度；冲突先核查 |
| 整体记录 | 阶段、批准、correction、当前指针、历史及证据是否齐备 | 按稳定身份补齐缺失项，保留已完成步骤和错误 |
| 环境与证据 | 实际进程、资源、产物、日志及源摘要 | 验证动作与日志写入分别判断，仅处理缺失部分 |

工具尾部报错不代表其此前副作用回滚。不能因工具退出失败就重复 commit、绕过 hooks、重放状态变化或丢弃既有成果。未能确定实际结果时先保持局部阻塞。

新会话发现任务已 `claimed` 时，核对持久 owner 与旧执行者已停止，再续接同一所有者；不要再次 `claim`，CLI 对非 pending 状态包括同 owner 的 claimed 也会拒绝。无法证明旧 writer 已停止时不得并行修改。没有超时回收或强抢命令。

## 4. 写入与去重

`delivery.json` 的唯一协调者和写入方式按 [delivery-flow 第 3 节](../SKILL.md#3-管理状态与确认依据)。恢复不改变该边界；子 Agent 返回结果，不并发维护整体状态。

批准和 correction 在首次记录时采用稳定 ID，重复录入前按 ID 及实际证据查找；相同事件补齐原项，不重复追加。旧记录无 ID 时，按阶段、任务/决策/修复范围、真实批准依据匹配，不能仅按一句相同回复合并不同批准。发现相同 ID 指向不同事实先解决冲突。

条件式推送授权按实际仓库、远端和需求分支范围恢复，不因验收完成再次索取相同批准。`delivery.json.pushes[]` 用仓库、remote/ref 和固定 commit 确定稳定身份，记录完整推送及核验结果；同一事实补齐原项，新的交付修订是新的推送事件。旧文件无 pushes 时兼容读取已有报告与真实远端证据，不修改原任务 result 或补造过去推送事实。

阶段历史仅在发生真实转移时追加；同阶段补证据不是新的转移。decide 重试前按决策 ID 核查既有日志，已有相同决策则引用，不直接编辑日志。CLI 状态只通过现有命令更新，不以去重为理由修改活跃 `project.json` 或 `decisions.jsonl`。

这些可选记录不要求旧实例迁移；恢复时兼容缺字段，模板更新不重建活跃交付。

恢复辅助脚本和中间载荷遵循 [产物管理](artifact-management.md)。重试不复制一套新状态清单或记录脚本：先确认当前入口、稳定事件 ID 和实际已完成副作用，再补缺失记录。历史 manifest 保留其对应修订，当前入口引用有效证据；旧目录布局不触发迁移或历史清理。
