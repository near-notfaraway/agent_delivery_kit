# 需求分析与澄清

将原始需求整理为可独立阅读、可供人工评审的 `requirement.md`。面向未参与聊天的产品、开发、测试和运维人员，明确问题、范围、业务行为与验收，记录实际澄清结论和确认版本。

## 调用范围与阶段边界

本 Skill 的职责终点是需求稿及其真实评审状态。需求确认后的阶段由协调者在实际授权范围内继续；本 Skill 不编写技术方案、实现代码或初始化执行控制。

由 mainAgent 直接执行或委派给通用/专业 subAgent，输入输出、路径和 writer 遵循 [委派约定](../delivery-flow/references/agent-delegation.md)。受委派时将业务问题与整稿确认请求返回 mainAgent；下文的用户对话由 mainAgent 组织，再由指定文档 writer 写回实际结论。用户直接使用本 Skill 时可直接澄清，不自动获得整体协调权。

先核验当前需求入口，再恢复属于本次交付的阶段及用户决定。参考材料中的旧确认不自动成为本次确认。某个问题的答复仅确认该事项，不能据此宣称整份需求已确认；会话中已有明确覆盖当前版本的阶段确认时，沿用其授权，不重复询问。文档生成或修改完成不代表通过评审。

## 1. 恢复输入和授权边界

读取工作区指令和本次分配的需求入口。按 [delivery-flow 的入口判定](../delivery-flow/SKILL.md#2-定位交付入口并判定新建或恢复) 区分当前需求稿与参考资料：当前目录及有效交付记录不存在时，先整理新需求；只有明确续接或采用且已核实的旧材料才能用于恢复基线。不要因为发现同名 requirement.md、design.md 或外部“已评审”记录就跳过需求整理与确认。

从已分类材料提取：

| 输入 | 使用方式 |
|---|---|
| 原始业务输入与参考文档 | 按来源性质识别出处、版本、目标、规则与建议，不从原文评审字样推断本次批准 |
| 需求名称、本次文档版本和分支约定 | 沿用本次指定值；新稿不继承参考文档版本，不自行换名或创建分支 |
| 文档保存位置 | 使用已授权目录或文档系统，保持稳定入口 |
| 相关仓库和组件 | 区分可能改动、仅作依据和其他团队负责的范围 |
| 本次有效确认和当前阶段 | 核验对应交付、版本及范围后恢复，避免重复确认和重复调研 |

能从现有材料查到的信息先查，不要求用户重复提供。缺失信息仅在影响下一阶段时询问，并继续完成不依赖该信息的工作。

遵守用户授权和工作区规则。真实业务材料只保存在授权的需求位置；公共 Skill、模板和示例只保留通用规则，不复制内部需求、链接、私有路径、代码、账号或凭证。

产物位置和当前入口按 [产物管理](../delivery-flow/references/artifact-management.md)。默认只维护 requirement.md；来源登记、原文收录及已有索引按 [来源材料管理](../delivery-flow/references/source-materials.md) 返回协调者，获分配来源写入范围时可执行该部分收录，不自行另建接入报告或资源清单。纯文档阶段不要求 attempt/runtime。

## 2. 阅读原始材料

实际读取正文及与当前需求有关的表格、评论、附件和引用资料；优先复用本次来源索引中的固定版本。在线来源可使用对应平台的读取工具或可选文档 Skill，也可读取用户提供的完整本地导出/正文，不要求特定平台 Skill。按来源材料管理登记用途、版本和实际读取范围，核对导出是否包含必要评论、附件及引用；不把搜索摘要当作正文。缺少材料时继续独立部分，影响范围或验收的缺口进入澄清，不能猜测内容或将未读资料写成已核实。

提取背景、业务目标、用户场景、本期范围、明确排除项、业务约束和验收条件。按依据区分：

- 原文明确要求。
- 用户后续确认的结论。
- 原文建议或可选方向。
- 尚未确认的假设。

建议不能直接变成已确认要求。材料之间出现矛盾时，先核对版本和已有结论；仍影响范围或验收的矛盾进入澄清问题。

## 3. 编写可评审需求稿

统一只交付一份 `requirement.md`，版本写在文件内部。先读取本 Skill 自带的标准模板 [assets/requirement_template.md](assets/requirement_template.md)，采用其元信息表、适用章节和确认记录，删除填写提示及不适用内容。模板路径相对本 Skill 解析，不依赖调用者的当前目录。

本 Skill 不生成版本后缀评审副本、接入报告、独立澄清或评审文件、执行材料，也不创建或修改 `delivery.json`。问题、结论、本次文档版本和确认都维护在 requirement.md；来源原文按上述分工收录，不是第二份需求稿。使用 `delivery-flow` 协调时，由协调者初始化或恢复 `delivery.json` 并同步阶段；独立需求文档工作不因此要求创建交付状态。

文档保留需求名称、输入来源、来源版本、实际读取范围、本次文档版本、更新日期和 `待澄清 / 待确认 / 已确认` 状态。有来源索引时引用该入口及关键来源名称/版本，不重复维护完整清单。正文表达当前有效规则；历史结论放在附录 A，注明效力及替代事项；修订与评审记录放在附录 B。

按模板覆盖背景与目标、范围与参与方边界、需求规则与验收、已确认系统约束、实际非功能要求、待确认与待核查事项、完成条件与文档确认。用稳定 R 编号及验收编号关联业务规则和通过标准。简单规则可合并成表格；筛选、排序、状态和时间边界等复杂规则单独展开，写清具体输入或操作和可观察结果。

围绕实际需求检查正常、异常和边界行为，尤其关注状态变化、时间边界、失败是否改变原数据、已有页面何时更新、存量行为、权限及环境隔离。资料未明确的行为标为待确认，不擅自补成要求。

只记录实际提出的非功能要求，不编造性能指标、数量上限、固定格式、权限模型或发布要求。需求正文以业务行为为主，不提前加入实现细节、Agent 任务、认领命令或执行状态。后续已有执行材料时仅在附录引用入口，不重复维护仓库配置或任务状态。

## 4. 澄清关键不确定事项

存在影响范围、预期行为或验收的不确定事项时，直接在对话中向用户澄清，每次只问少量关键问题并说明影响；有建议时给出依据。不先生成单独的评审补充稿或问题报告。如果没有此类问题，就交付 `requirement.md`，不为填模板编造澄清问题。

能通过代码或文档确定的技术事实先自行核查。第 6 节区分需求澄清、技术设计和执行配置事项，标明是否阻塞对应阶段；仅在核查结果影响业务选择或验收口径时，才升级为用户确认事项。既有错误处理和再次查询已满足需求时直接复用，不默认增加专门状态或恢复交互。

为澄清做必要的定向只读调研，不提前展开完整技术设计。默认不修改业务代码、不切换分支、不运行会变更依赖或生产数据的命令。

局部技术实现选择可以基于证据留给技术设计阶段；会改变产品语义或范围的选择需用户确认。

记录稳定问题编号（如 Q1）、问题、影响、真实结论、确认日期及依据。用户回应后，将结论写回对应需求正文并同步验收条件；清理冲突假设，不只在文档末尾追加聊天结论。已解决问题进入附录 A，当前待确认列表只展示未解决事项。

需要进入技术设计而缺少整稿确认时，先交付完整的 `requirement.md`，再确认对应版本。使用模板第 7 节的当前确认记录，写清实际确认人、时间、版本和范围；未实际确认的字段保持待确认。只有需求文档交付的请求到此结束，不因没有澄清问题自行进入设计。

## 5. 处理变更

收到反馈后直接更新已授权的需求文档。区分业务规则、范围、验收和表达方式的变化，保持稳定需求编号，更新版本及真实 Review 记录。

已有技术方案或外部对接材料时，识别受影响契约并按授权同步；涉及新的产品语义时记录待确认状态。已有执行快照的变更遵守工作区基线同步流程，不直接修改活跃执行状态。

## 6. 输出前润色

每次向用户输出新稿或修订稿前，先在同一份 `requirement.md` 中完成一轮润色，再执行下一节的交付检查。沿用已有文档入口、版本和确认约定。环境中有适合需求文体的润色 Skill 时可选用；没有时直接按以下步骤执行。

1. 通读正文，理顺长句、重复、空话和不清楚的指代，使用自然、准确的中文表达。保留必要业务术语，已经通顺的内容不强行改写。
2. 保留业务范围、规则、验收标准、非功能要求及出处，完整保留条件、否定、时间和确定程度。不补造事实或指标，不把建议、假设或待确认事项改成已确认要求，也不为缩短篇幅删除独立信息。
3. 默认保留标题文字与层级、稳定需求/验收/问题编号、表格数据、字段名、代码块、命令、路径、URL、链接目标及原始引文。确需调整标题或引用时，按既有文档规范核查受影响引用。
4. 对照润色前的文本逐段核对信息和语义，再通读成稿，检查术语、指代及上下文是否一致。发现规则矛盾或资料缺口时，按原澄清或变更流程处理，不用措辞掩盖问题。

润色完成不代表需求通过评审；实际确认及基线同步仍遵循已有流程。润色后的版本作为交付检查和人工评审的入口。

## 7. 检查与交付

交付前检查：

- 已完成输出前润色，并对照原稿确认信息、语义和确定程度未被改变。
- 已确认结论全部写入正文，旧建议和假设没有冒充要求。
- 范围、状态、字段、时间及错误行为一致，关键异常和边界可验收。
- 待确认问题均说明影响，局部确认和整份需求确认有明确区分。
- 当前交付材料与参考来源已经区分；来源、版本、读取范围和 Review 记录可追溯，必要原文已收录或明确缺口，读者无需聊天补全关键规则。
- 人工需求评审入口仅为 `requirement.md`，遵循标准模板；来源副本按分配范围保存，正文、历史结论和当前确认范围一致，被替代结论已标记。
- 没有额外引入功能、仓库、基础设施、执行计划或无依据的指标。

进行适当的内容、链接和一致性检查，并遵守工作区验证要求；不因需求文档整理新增业务测试或宣称通过业务验收。

交付时提供 `requirement.md` 入口，简述实际文档状态；有澄清事项直接在对话中提出。没有澄清事项时交付这一份文档即可。只有存在真实用户确认依据时，才标记对应版本“已确认”。

## 调用示例

> 请读取这份需求及相关评论，沿用已有名称和授权目录，整理 requirement.md。先核查能查到的事实，澄清影响范围与验收的关键问题，把结论写回正文，需求确认后再进入技术设计。
